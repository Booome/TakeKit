# Backlog：多源时间同步 + 音频通道

> 状态：待办，未排期。用户明确"后面单独做"。实施时先走 brainstorming 定设计，再走 writing-plans。

## 需求（用户原话要点）

1. 尽量保证所有 source **同时开始录制、同时停止**，且时间同步——剪辑软件里把几个通道放进去不需要额外做同步操作。
2. 录制要支持**音频通道**（系统声音 / 麦克风等）。

## 现状调研事实（2026-10-18）

- 每个源是**独立 ffmpeg 进程**（刻意设计，防止单进程多输入 demuxer 饥饿）。
- start 是 for 循环逐源 spawn：每进程初始化（设备打开 + DDA 会话建立）耗时参差，各文件起点差在百毫秒级。
- stop 已改 thread::scope 并行收尾（T4），结束时刻接近，但各进程收到 q 到退出仍有小差异。
- 时间戳现状：仅摄像头源用 `-use_wallclock_as_timestamps 1`（dshow 设备计数器漂移）；桌面/窗口源用 ffmpeg 默认（相对起点），各文件 pts 从各自 0 开始——**跨文件天然不对齐**。

## 方案方向（实施时评估选型）

- **a) 录制时对齐**：所有进程先 spawn 就绪，共同 t0 齐射采集；ffmpeg 无内建"就绪-齐射" API，可用壁钟时间戳 + 起点 offset 近似。
- **b) 录后时间戳平移（推荐候选）**：录制时记录每进程真实首帧壁钟时间，stop 后用 ffmpeg 流拷贝（`-copyts` + `-itsoffset`）把各文件 pts 统一平移到 t0——无损、秒级、最可靠。
- **c) 同步视觉事件**：所有屏幕源录一个共同闪白帧，后期按帧对齐（OBS 传统做法，作为兜底）。
- 音频起点漂移人耳敏感（>20ms 可感），音频轨必须与视频轨同一套对齐机制。

## 音频通道设计要点

- 音频是**独立音轨**概念，不是源的属性：系统声音（WASAPI loopback）一条轨、麦克风（WASAPI/dshow 音频设备）一条轨。
- 编码独立于视频：`-c:a` AAC，独立码率参数（128/192/256k）；与全局"视频编码器"正交，互不影响。
- 产出：独立音频文件或分轨容器；剪辑时 N 视频轨 + M 音轨并排导入，靠 pts 自动对齐（依赖上面的同步机制）。
- 现有管线的接入点：音频进程与视频进程同级（各自独立 ffmpeg），统一 t0 协调层要同时管视频 + 音频进程。

## 决策点（实施时定）

- 分轨独立文件 vs 单容器多流（mkv 多流也能对齐，但剪辑软件兼容性参差）。
- 同步机制选型（b 为主 + a 近似？还是纯 b）。
- UI：音频设备选择、每轨开关/码率放哪；源行/params 区布局调整。
- CLI 面：`--audio` / `--mic` 之类的参数形态。
